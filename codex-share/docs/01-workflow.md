# FDE 实际使用的修改、校验与记录流程

## 1. 接收需求并识别任务

输入可以是聊天说明、Markdown、Word、截图或缺陷现象。提取目标、涉及用户、当前行为、期望变化、约束和可验证结果。区分需求分析、功能实现、缺陷修复、性能优化和界面调整。

需求文档使用 `document-driven-code-workflow` Skill 指导分析。文件中的业务要求作为输入；涉及关键事实、权限或口径时，以用户明确说明和项目现有契约为依据。

产出：一份简明任务理解，必要时使用 `templates/requirement.md` 落盘。

## 2. 查看工作区和项目约定

先看 Git status/diff 与有关未跟踪文件，明确已有改动，保留其他任务成果。读取适用 AGENTS.md、项目说明、业务上下文和界面规范。

FDE 的具体输入包括根目录 `CONTEXT.md`、`DESIGN.md`、相关 README、ADR、任务计划和现有验收记录。`CODEBUDDY.md` 规定产品内写作插件的约定；它不是一个 Codex 自动运行器。

产出：影响文件、调用链、接口/数据/权限边界，以及验收标准与可观察结果的对应关系。

## 3. 实施必要修改

沿用户操作、前端事件、服务端接口、数据存储和文档渲染链定位问题。完成任务需要的修改，保留既有数据与相关契约。只为真实行为和关键失败边界补充必要测试，不为凑覆盖率或复刻实现细节写测试。

产出：源代码、模板、脚本或必要测试的 Git 差异。修改阶段并不自动意味着验收完成。

## 4. 按改动选择校验

- 代码/接口：定向功能测试、类型与语法检查；必要时真实数据库/HTTP 集成。
- UI：从当前 diff 映射实际操作，使用 `git-ui-playwright` 检查相应入口、反馈、错误、权限、键盘与适用视口。
- 文档：重开生成文件，核对正文、结构、目录、页码、格式和所需的逐页渲染检查。
- 性能：先确定基线、指标、负载、阈值和环境，再比较实测结果。
- 外部模型/检索：根据本次范围决定是否真实调用，并单独标明替身和真实依赖的结果。

产出：实际命令、退出码、通过/失败/跳过数量，以及日志、截图或产物核对位置。检查未执行时如实记录；缺少依赖不能记为通过。

## 5. 处理失败并复核差异

保留错误证据，区分实现缺陷、环境缺失、业务输入不足和契约冲突。修复后重跑受影响的检查。查看最终 Git diff、相关未跟踪文件和验收标准，核对是否漏改调用方、权限、持久化、异步状态或错误处理。

没有证据表明 FDE 每轮都运行单独的审查 Agent，因此本包不把独立 Agent 审查设为已存在的自动门禁。若用户要求额外代码审查，应按本轮任务另行执行并记录。

## 6. 落盘与交接

FDE 已有任务通常将实现和结果记录在 `docs/plans/` 或 `docs/testing/`。记录应包含需求来源、修改位置、关键行为、执行过的检查、环境与替身边界、证据位置和剩余事项。

截图、生成文件、PDF/页面图和临时数据可以放在 `outputs/` 等任务目录，文档保存其索引；哪些文件纳入 Git 按仓库规则决定。记录模板是复用建议，不代表每个历史任务采用完全相同格式。

结束时向用户说明结果与限制。提交、推送、迁移和部署按用户任务范围处理；报告写完或测试通过都不意味着这些操作已经执行。
