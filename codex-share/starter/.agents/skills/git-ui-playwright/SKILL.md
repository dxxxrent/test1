# Git UI Playwright

针对当前 Git 修改涉及的界面和用户流程做本机浏览器点检。不要把一次有范围的变更测试扩展成全站审计。

## 工作流程

1. **确定 Git 测试范围。** 查看 `git status --short --branch`、`git diff --stat`、`git diff` 和 `git diff --cached`。同时检查相关未跟踪文件，但不要擅自暂存它们。若工作区干净，按当前分支的上游或用户指定的基线查找变更；基线不明确时，先说明采用的范围。
2. **从变更映射到用户操作。** 阅读修改文件及其相邻页面、事件处理、权限判断、API 调用和已有测试。列出会受影响的页面、用户角色、操作步骤和可观察结果。后端/API 改动若改变界面行为，也纳入对应流程。
3. **识别本地运行方式。** 读取 `package.json`、项目说明、测试配置和相关脚本。优先复用已有本机启动命令、Playwright 浏览器、测试夹具和 API mock。不要读取 `.env` 中的密钥。优先连接可用的本机服务；没有用户明确要求或项目本机流程确实需要时，不要用 Docker。
4. **安全启动与重启。** 检查目标地址是否已有服务并确认其来源，能复用就复用。后端使用 watch 模式时，等待自动重启；静态前端文件更新后刷新页面。需要手动重启时，只停止本次启动的进程，不要结束不明来源的进程。缺少数据库、浏览器或配置时，运行不依赖它的 UI 用例，并报告受阻的完整流程和所需条件。
5. **用 Playwright 覆盖受影响的功能。** 优先执行最贴近变更的现有测试；若覆盖不足，补充或临时编写窄范围 Playwright 用例。使用可访问名称、角色和标签定位元素，避免脆弱的长 CSS/XPath 选择器。每条流程至少验证用户操作及其结果，不以“页面能打开”代替功能测试。
6. **检查可见结果和失败。** 对视觉或响应式改动，检查常用桌面尺寸；仅在变更涉及窄屏或共享布局时增加窄屏检查。收集浏览器页面错误、相关 API 失败、断言结果和必要截图。检查键盘焦点与键盘操作，前提是变更涉及可操作控件。
7. **完整业务流程使用隔离数据。** 上传、创建项目、运行生成或下载等端到端流程，只在本机/测试环境使用专用数据执行。优先 mock 外部模型、服务和计费型依赖；真实外部调用仅在用户明确要求时执行。清理测试自己创建的数据和文件，不清理已有用户数据。
8. **报告结论。** 简要说明 Git 范围、执行的页面流程、所用命令、浏览器视口、截图或日志位置、通过/失败项，以及因环境条件未能覆盖的步骤。不要声称执行了未运行的测试，也不要把 mock 结果描述为真实外部服务验证。

## 本机 Playwright 选择

- 若项目使用 Playwright Test，按项目配置运行对应测试文件/用例；不要假设仓库已安装 `@playwright/test`。
- 若项目用 Node `node:test` 封装 Playwright，使用项目现有命令，例如 `node --import tsx --test test/<相关用例>.test.ts`。
- 手动可见点检可使用 `npx playwright open --browser=chromium <本机地址>`；记录操作可用 `npx playwright codegen --browser chromium <本机地址>`。CLI 打开或录制操作本身不算自动化断言通过。
- 若 Playwright 包或浏览器缺失，先查项目已有浏览器路径和锁定依赖。不要自行升级依赖或运行安装器；说明缺失项和项目认可的安装命令。
- 不要为了运行 UI 检查覆盖用户现有的 `.env`、数据库或未提交修改。

## 验收原则

- 覆盖 Git 变更直接影响的主路径及相关权限/错误状态，不要求无关功能通过本次点检。
- 断言可观察的结果：导航/内容变化、按钮状态、保存/上传/运行响应、下载产物或用户可见反馈。
- 记录未覆盖原因；服务或模型不可用时，不要把模拟数据下的 UI 检查说成真实业务端到端通过。
